# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AMCAS: address-mapping and row-buffer policy optimization for transformer (LLM attention and MoE) DRAM access patterns. We capture the DRAM request stream of llama.cpp inference, replay it through DRAMsim3 and Ramulator 2.1 under different mappings and page policies, and work toward a mapping or policy proposal. The problem statement and literature survey are in `problem_stmt_and_literature_survey.tex`.

- `context.md`: the running project log (state, decisions, build details, results, handoffs). Read it first. **It is append-only: add new sections, never delete or rewrite earlier content.**
- `ANALYSIS.md`: the written analysis of the gem5-era experiments.
- `analysis/`: `tables.md` and `fig_*.png`, generated by `tools/report.py`. Do not hand-edit.
- `cluster-data/`: results and logs auto-published from the cluster. Treat it as generated data.

There is no test suite, linter or local build. All computation runs on the RCE Slurm cluster. The laptop holds the source of truth for code and docs.

## Cluster workflow

- SSH: `ssh adityaseshasai.s@rce.iiit.ac.in`, through the NetworkManager VPN `iiit` in split-tunnel mode. The cluster mirror is `~/amcas-pro/`, with `configs/ patches/ tools/ scripts/` matching `trace-pipeline/`, plus `tracing/` (gem5, llama.cpp, DRAM simulators, models, micromamba envs), `results/` and `logs/`.
- **Code flows one way, laptop → cluster.** Sync edited `trace-pipeline/` files to `~/amcas-pro/` before submitting a job; `publish.sh` never copies scripts back. `sbatch` snapshots a script when it is submitted, so a queued job keeps the old version.
- **Results flow cluster → GitHub → laptop.** Jobs end by calling `tools/publish.sh "msg" [RUN...]`. It rsyncs files under 50 MB into a clone at `~/amcas-repo/cluster-data/`, reruns `report.py`, commits and pushes. Named runs' raw `dram.trc.gz` go to release `traces-2026-11-03` via `scripts/09_upload_traces.sh`. The cluster commits to `main` on its own, so **`git pull --rebase` before editing locally.**
- The GitHub token lives at `~/.config/amcas/gh_token` (mode 600). Pass it only through stdin or a credential helper, never on a command line or in output.
- Python environments: `~/amcas-pro/tracing/mamba/envs/gem5` (gem5 toolchain, no matplotlib) and `.../envs/analysis` (report generation). The login node's system Python is 3.6. numpy there needs `OPENBLAS_NUM_THREADS=1`.
- Jobs exclude GPU nodes `node04,node05`. Full-scale native work runs on `node01` (2× Xeon Gold 6226R, AVX-512, 384 GB RAM, node-local `/scratch`). Home quota is 100 GB, so large traces go to `/scratch`.
- Check jobs with `squeue -u $USER` and `sacct -X --starttime=... --format=JobID,JobName%22,State,ExitCode,Elapsed`.

## Pipeline architecture (`trace-pipeline/`)

Scripts are numbered in dependency order. Two eras share them:

**gem5 capture (small models: stories15M, Qwen2.5-0.5B, tinymoe4)**
1. `01`, `02`, `05`: build the micromamba env and gem5 (`gem5.opt` and `gem5.fast` with tcmalloc), and llama.cpp `build-gem5`. `patches/apply_patches.py` (idempotent) adds a `vaddr` field to gem5's packet trace. It also wraps each llama.cpp graph compute in `m5_work_begin/end` and dumps tensor addresses to `amcas_tensors.tsv`, but only under `-DAMCAS_M5`.
   - llama.cpp for gem5 is static and SSE2-only: gem5 X86 has no AVX and miscomputes SSSE3.
   - Logging is inline, because SE mode cannot `clone()` a logger thread.
   - `HOME` must be set, or glibc's NSS breaks inside SE mode.
2. `configs/llm_trace.py`: gem5 SE config. A `CommMonitor` between membus and the DRAM controller traces exactly what a controller receives (LLC misses, writebacks, prefetches).
   - It fast-forwards atomically with warm caches, then switches to O3 at a work-item boundary (`--detail-from`).
   - Phase 0 is the prompt; each later phase is one token.
3. `04_trace.sh NAME MODEL CTX N [llm_trace.py opts]`: one capture into `results/traces/NAME/`. `SESSION=BASE` restores a prompt saved by `08_long_context_native.sh` (`CTX` must match `BASE.ctx`).
   ```bash
   sbatch --export=ALL,GEM5=gem5.fast -J NAME -o logs/trace/NAME_%j.log scripts/04_trace.sh \
     NAME MODEL CTX N_PREDICT --detail-from 1 --max-work-items 2 --l3 22MiB --l3-assoc 11 --prefetch stride
   ```
4. `tools/pkt2bin.c`: hand-parses the protobuf trace into 40-byte records (`dram.bin`), because gem5's Python decoder cannot handle hundreds of millions of records.
5. `tools/analyze.py RUN_DIR`: validates against `stats.txt` and attributes accesses to tensors through `vaddr` and `amcas_tensors.tsv`. It writes `summary.json` and exports `dram.dramsim3.trc` and `dram.ramulator.trc`.
   - Only detailed phases count. The atomic phase 0 is excluded from totals and exports.
6. `06_dram_sims.sh RUN`: DRAMsim3 grid (`rochrababgco`/`rocorababgch` × open/close page), replayed at trace timestamps. Then `tools/ramulator_replay.py`: Ramulator 2.1, saturated with no timestamps, over mappers RoBaRaCoCh/MOP4CLXOR/ChRaBaRoCo × Open/ClosedCAP. Both replays are open-loop.
7. `tools/report.py RESULTS_DIR OUT_DIR`: cross-run tables and figures. To add a run, add it to its `RUNS` list (and `LABEL`).

**Full-scale (Qwen2.5-0.5B, Qwen2.5-7B, Qwen3-30B-A3B)**
- `10`: downloads models, checked against Hugging Face SHA-256. `11`: `build-fast`, native AVX-512 with OpenMP. `12`: native thread and batched-decode benchmarks into `results/fullscale/native/`.
- `13_dynamorio_check.sh`: feasibility check of DynamoRIO `drmemtrace` on native multithreaded llama.cpp. It skips installation if `tracing/dynamorio/bin64/drrun` already exists. The cluster's glibc is 2.28, so use a stable DynamoRIO release; cronbuilds need 2.34.
- Planned route: drmemtrace → cache model → physical placement → closed-loop Ramulator, validated against the gem5 Qwen 0.5B traces. `publish.sh` will run `tools/fullscale_report.py` if that file exists.

## Conventions

- Validate any new capture or replay against native output (generated text, controller read/write counts) before trusting its numbers. `report.py` already checks this for the gem5 runs.
- Record findings, job IDs and decisions in `context.md` as new dated sections.
- `.gitignore` excludes `*.trc.gz`, `*.trc`, `*.bin`, `*.session`, `*.gguf`. Raw traces live only in the GitHub release.
